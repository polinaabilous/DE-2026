Window basics · the one idea everything else builds on

GROUP BY collapses rows. A window keeps them.

Both queries add up amounts per customer. The difference is what happens to the rows.

Compare the two results
SQL
SELECT customer, SUM(amount) AS customer_total
FROM orders
GROUP BY customer;
customercustomer_total
Ana40
Leo100
Maya80

Six rows went in, three came out. The individual orders are gone.

SQL
SELECT order_id, customer, amount,
       SUM(amount) OVER (PARTITION BY customer) AS customer_total
FROM orders;
order_idcustomeramountcustomer_total
1Maya2580
2Maya4080
3Leo40100
4Maya1580
5Leo60100
6Ana4040

Six rows went in, six came out. Each order also carries its customer’s total.

What is a window?

A window is the set of rows a function is allowed to look at for the current row. OVER (…) defines it.

Why it matters

You can now compare a row with its group in one pass: “what share of Maya’s spend is order 2?” needs both the order amount and Maya’s total on the same row.

The main idea

if the question needs detail rows and a group-level number side by side, you want a window function, not GROUP BY.

03

Window basics · three optional parts, always in this order

The anatomy of OVER ( )

SQL
function_name(args) OVER (
    PARTITION BY customer          -- 1. split rows into independent groups
    ORDER BY order_date            -- 2. sort rows inside each group
    ROWS BETWEEN UNBOUNDED PRECEDING
         AND CURRENT ROW           -- 3. frame: which sorted rows count right now
)

01PARTITION BY

“Per what?” Restarts the calculation for each group. Leave it out and the whole result set is one partition.

02ORDER BY

“In what sequence?” Required for ranking and LAG/LEAD. For aggregates it turns a group total into a running total.

03Frame

“Which rows up to or around me?” Only used by aggregate and value functions. If you omit it, a default applies — next slides.

The main idea

read every window aloud as “for each partition, in order, looking at frame”. If you cannot finish that sentence, the query is not ready.

04

Window basics · logical query processing order

When do window functions run?

SQL is written SELECT-first but evaluated in a different order. Windows are computed late — after grouping, before the final sort.

01
FROM / JOINbuild the row set

Tables are combined.

02
WHEREfilter rows

Window results do not exist yet, so you cannot filter on them here.

03
GROUP BY → HAVINGaggregate and filter groups

Windows see the grouped rows, so SUM(SUM(amount)) OVER () is legal.

04
Window functionscompute OVER (…)

Evaluated on the rows that survived.

05
SELECT → DISTINCTpick and dedupe columns

Aliases are created here.

06
ORDER BY → LIMITsort and cut

You may ORDER BY a window alias.

So how do I filter on a rank?

Wrap it: compute the window in a CTE, filter in the outer query. Some engines (Snowflake, BigQuery, Databricks, DuckDB, Teradata) add QUALIFY as a shortcut.

Example

SQL
WITH ranked AS (
  SELECT order_id, customer,
         ROW_NUMBER() OVER (PARTITION BY customer
                            ORDER BY order_date DESC) AS rn
  FROM orders
)
SELECT order_id, customer
FROM ranked
WHERE rn = 1;   -- each customer's latest order
The main idea

“window function in WHERE” is a classic interview error. Say it out loud: “windows run after WHERE, so I’ll filter in an outer query.”

Five families of window functions

FamilyFunctionsQuestion it answersORDER BY?

Window functions · ranking · ROW_NUMBER()

ROW_NUMBER: a unique sequence per group

Number each customer’s orders

SQL
SELECT customer, order_date, order_id,
       ROW_NUMBER() OVER (
         PARTITION BY customer
         ORDER BY order_date, order_id
       ) AS order_seq
FROM orders;
customerorder_dateorder_seq
Ana2026-01-101
Leo2026-01-051
Leo2026-01-102
Maya2026-01-031
Maya2026-01-052
Maya2026-01-093

How it behaves

Always 1, 2, 3… with no gaps and no ties, even if two rows are identical on the ORDER BY columns.

That means ties are broken arbitrarily unless you add a tie-breaker. Two runs of the same query can number tied rows differently — a real source of flaky pipelines.

Use it for: “exactly one row per group” (dedupe, latest record), first purchase vs repeat purchase, pagination, and the gaps-and-islands trick.

The main idea

ROW_NUMBER guarantees exactly one row per position. Always end its ORDER BY with a unique column so the result is deterministic.

Window functions · ranking · the tie question

ROW_NUMBER vs RANK vs DENSE_RANK

Rank all orders by amount, highest first. Three orders tie at 40.

SQL
SELECT order_id, amount,
       ROW_NUMBER() OVER (ORDER BY amount DESC) AS row_number,
       RANK()       OVER (ORDER BY amount DESC) AS rank,
       DENSE_RANK() OVER (ORDER BY amount DESC) AS dense_rank
FROM orders;

order_idamountROW_NUMBERRANKDENSE_RANK
560111
240222
340322
640422
125553
415664

RANK — “Olympic” ranking

Ties share a rank, then the next rank skips (1, 2, 2, 2, 5). Use when position should reflect how many rows are ahead.

DENSE_RANK — no gaps

Ties share a rank, next rank is consecutive (1, 2, 2, 2, 3). Use for “Nth highest distinct value” and “top 3 salary levels”.

ROW_NUMBER — no ties

Forces 2, 3, 4 on the tied rows. Order among them is arbitrary here — add order_id to make it stable.

The main idea

in an interview, ask “how should ties be handled?” before writing a ranking query. The answer picks the function.

Window functions · distribution · buckets and percentiles

NTILE, PERCENT_RANK, CUME_DIST

SQL
SELECT order_id, amount,
       NTILE(4)       OVER (ORDER BY amount DESC) AS quartile,
       PERCENT_RANK() OVER (ORDER BY amount DESC) AS pct_rank,
       CUME_DIST()    OVER (ORDER BY amount DESC) AS cume_dist
FROM orders;

order_idamountNTILE(4)PERCENT_RANKCUME_DIST
56010.000.17
24010.200.67
34020.200.67
64020.200.67
12530.800.83
41541.001.00

NTILE(n)

Deals rows into n buckets as evenly as possible; earlier buckets get the extra rows (6 rows / 4 = 2, 2, 1, 1). Ties can be split across buckets — orders 2 and 3 both have 40 but land in different quartiles.

PERCENT_RANK

(rank − 1) / (rows − 1). Ranges 0 to 1. “What fraction of rows are ranked above me?” Ties share a value.

CUME_DIST

rows at or before me (including peers) / rows. Ranges just above 0 to 1. “Top 10%” ⇒ CUME_DIST() <= 0.10 when ordering descending.

The main idea

NTILE for “split into equal-size groups”; PERCENT_RANK / CUME_DIST for “top X percent” where ties must stay together.

Window functions · offset · LAG(col, n, default) / LEAD(col, n, default)

LAG and LEAD: look at the neighbour row

Maya’s order-to-order change

SQL
SELECT order_date, amount,
       LAG(amount)  OVER w AS prev_amount,
       LEAD(amount) OVER w AS next_amount,
       amount - LAG(amount) OVER w AS change,
       order_date - LAG(order_date) OVER w
                                AS days_since_prev
FROM orders
WHERE customer = 'Maya'
WINDOW w AS (PARTITION BY customer
             ORDER BY order_date);
order_dateamountprevnextchangedays
01-0325NULL40NULLNULL
01-05402515+152
01-091540NULL−254

How it behaves

LAG(x) returns x from the previous row in the window order; LEAD(x) from the next. The optional second argument is the offset (LAG(x, 7)), the third is a default instead of NULL (LAG(x, 1, 0)).

The first row has no predecessor, so LAG returns NULL — and any arithmetic with it is NULL. Decide whether that should be NULL, 0, or filtered out.

The WINDOW w AS (…) clause names a window once and reuses it (PostgreSQL, MySQL 8, SQLite, BigQuery, DuckDB, SQL Server 2022).

Use it for: month-over-month change, time between events, detecting status changes, sessionization.

The main idea

whenever a question compares a row with “the previous one” or “the next one”, reach for LAG/LEAD instead of a self-join.

Window functions · value · and the LAST_VALUE trap

FIRST_VALUE, LAST_VALUE, NTH_VALUE

Run LAST_VALUE with two frames
SQL
SELECT order_date, amount,
       FIRST_VALUE(amount) OVER (PARTITION BY customer ORDER BY order_date) AS first_amt,
       LAST_VALUE(amount)  OVER (PARTITION BY customer ORDER BY order_date) AS last_amt
FROM orders WHERE customer = 'Maya';
order_dateamountfirst_amtlast_amt
01-03252525
01-05402540
01-09152515

LAST_VALUE just echoes the current row: the default frame stops at CURRENT ROW, so the “last” row in the frame is me.

SQL
SELECT order_date, amount,
       FIRST_VALUE(amount)  OVER w AS first_amt,
       LAST_VALUE(amount)   OVER w AS last_amt,
       NTH_VALUE(amount, 2) OVER w AS second_amt
FROM orders WHERE customer = 'Maya'
WINDOW w AS (PARTITION BY customer ORDER BY order_date
             ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING);
order_dateamountfirst_amtlast_amtsecond_amt
01-0325251540
01-0540251540
01-0915251540

With the frame widened to the whole partition, every row sees Maya’s first, last, and second order amounts.

Tip: LAST_VALUE(x) OVER (ORDER BY d) can also be written as FIRST_VALUE(x) OVER (ORDER BY d DESC), which needs no frame. NTH_VALUE is not available in SQL Server.

The main idea

value functions respect the frame. For “first/last in the group”, use a full frame or flip the sort and use FIRST_VALUE.

Window functions · aggregate · same functions, new superpower

SUM, AVG, COUNT, MIN, MAX as windows

SQL
SELECT customer, order_date, amount,
       SUM(amount) OVER (PARTITION BY customer ORDER BY order_date
                         ROWS UNBOUNDED PRECEDING)          AS running_total,
       ROUND(100.0 * amount
             / SUM(amount) OVER (PARTITION BY customer), 1) AS pct_of_customer,
       amount - AVG(amount) OVER ()                         AS vs_avg
FROM orders
WHERE customer = 'Maya';   -- note: AVG OVER () here is Maya's average, because WHERE ran first

order_dateamountrunning_totalpct_of_customervs_avg
01-03252531.3−1.67
01-05406550.0+13.33
01-09158018.8−11.67

With ORDER BY → running

Cumulative revenue, running count of orders, “max so far” (MAX(x) OVER (ORDER BY d)) for record highs.

Without ORDER BY → whole group

Share of total, difference from group average, “flag rows above their group’s mean”. Multiply by 100.0 to avoid integer division.

Windows over aggregates

Because windows run after GROUP BY: SUM(amount) * 100.0 / SUM(SUM(amount)) OVER () gives each customer’s share of all revenue in one grouped query.

The main idea

every aggregate you know becomes a window function by adding OVER. ORDER BY in the window decides “so far” vs “whole group”.

Interview patterns · say this out loud before typing

A four-question method for any window problem

  1. What is one output row? (the grain) — one per order? per customer? per day? This tells you whether you need GROUP BY, a window, or both.
  2. Per what? → PARTITION BY. “For each customer” ⇒ PARTITION BY customer. “Overall” ⇒ no partition.
  3. In what order? → ORDER BY inside OVER. “Latest” ⇒ date DESC. “Highest” ⇒ amount DESC. Add a unique tie-breaker.
  4. Which family? position → ranking; neighbour → LAG/LEAD; “so far” / group total → aggregate; bucket → distribution.
  5. Filter after. Put the window in a CTE and filter in the outer query (or QUALIFY where supported). Then test against ties, NULLs, and single-row groups.

Example: “For each customer, return their single biggest order.” Grain: one row per customer. Per: customer. Order: amount DESC, order_id. Family: ranking → ROW_NUMBER (one row, even with ties). Filter: rn = 1.

The main idea

narrating grain → partition → order → family → filter shows the interviewer structured thinking even before the SQL is perfect.

Interview patterns · “top 2 orders per customer”

Pattern: top N per group

The query

SQL
WITH ranked AS (
  SELECT customer, order_id, amount,
         DENSE_RANK() OVER (
           PARTITION BY customer
           ORDER BY amount DESC
         ) AS amount_rank
  FROM orders
)
SELECT customer, order_id, amount
FROM ranked
WHERE amount_rank <= 2
ORDER BY customer, amount_rank;

Choosing the ranking function

RequirementUse
Exactly N rows per group, ties broken somehowROW_NUMBER + tie-breaker
Top N values; include everyone tiedDENSE_RANK
Top N positions; ties may push past NRANK

Leo’s result: order 5 (60, rank 1) and order 3 (40, rank 2). Maya: 40 and 25. Ana: only one order, so one row — confirm that is acceptable.

Snowflake / BigQuery / DuckDB shortcut: QUALIFY DENSE_RANK() OVER (…) <= 2.

The main idea

top-N per group = rank inside a partition, filter outside. The interview follow-up is always “what about ties?”

Interview patterns · the most common data-engineering use

Pattern: deduplicate and keep the latest row

A CDC feed delivered the same customer three times. We want the current version of each customer.

Raw rows

customer_idemailupdated_atload_id
7a@old.com2026-01-01 09:001
7a@new.com2026-01-04 12:002
7a@new.com2026-01-04 12:003
8b@x.com2026-01-02 08:001

Keep one row per key

SQL
WITH ranked AS (
  SELECT customer_id, email, updated_at,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY updated_at DESC,
                    load_id    DESC   -- tie-breaker
         ) AS rn
  FROM customer_changes
)
SELECT customer_id, email, updated_at
FROM ranked
WHERE rn = 1;

Why not SELECT DISTINCT? It only removes rows identical in every column. Why not GROUP BY customer_id with MAX(updated_at)? You then need a join back to fetch the other columns — and ties still return duplicates.

The main idea

“latest per key” and “remove duplicates” are both ROW_NUMBER … = 1. The tie-breaker is what makes the pipeline repeatable.

Interview patterns · “cumulative revenue” and “7-day rolling average”

Pattern: running totals and moving averages

Aggregate to the grain first

SQL
WITH daily AS (
  SELECT order_date, SUM(amount) AS revenue
  FROM orders
  GROUP BY order_date
)
SELECT order_date, revenue,
       SUM(revenue) OVER (ORDER BY order_date
             ROWS UNBOUNDED PRECEDING)          AS cumulative_revenue,
       AVG(revenue) OVER (ORDER BY order_date
             ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
                                                AS rolling_7_row_avg
FROM daily;

Two traps interviewers probe

Missing days. ROWS 6 PRECEDING means 6 rows, not 6 days. Our data has no orders on Jan 4, 6, 7, 8, so a “7-row” window spans far more than a week. Fix: join to a calendar (recursive CTE, later) or use RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW where supported.

Partial windows. The first six days average fewer than 7 values. If that matters, also compute COUNT(*) OVER (same frame) and show NULL when it is below 7.

The main idea

aggregate to one row per period, make sure every period exists, then apply an explicit ROWS frame.

Interview patterns · month-over-month, year-over-year

Pattern: period-over-period change

Month-over-month growth

SQL
WITH monthly AS (
  SELECT DATE_TRUNC('month', order_date) AS month,
         SUM(amount)                     AS revenue
  FROM orders
  GROUP BY DATE_TRUNC('month', order_date)
)
SELECT month, revenue,
       LAG(revenue) OVER w AS prev_revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER w)
             / NULLIF(LAG(revenue) OVER w, 0), 1) AS pct_change
FROM monthly
WINDOW w AS (ORDER BY month);

Details that earn points

Year-over-year on monthly rows: LAG(revenue, 12) OVER (ORDER BY month) — only correct if all 12 months exist. Safer: self-join on month - INTERVAL '1 year', or fill months first.

Divide safely: NULLIF(prev, 0) avoids divide-by-zero; 100.0 avoids integer division.

Per segment: add PARTITION BY region so each region compares with its own previous month.

The main idea

period-over-period = aggregate per period, then LAG. Mention gaps and divide-by-zero before the interviewer does.

Interview patterns · “users who logged in 3+ days in a row”

Pattern: consecutive streaks (gaps and islands)

Consecutive dates increase by 1 each day; ROW_NUMBER also increases by 1 each row. Subtract one from the other and every date in the same streak gets the same anchor value.

See the trick

login_daternlogin_date − rnstreak
01-01112-31A
01-02212-31A
01-03312-31A
01-05401-01B
01-06501-01B
01-09601-03C

The query

SQL
WITH days AS (
  SELECT DISTINCT user_id, login_date
  FROM logins                 -- one row per day!
), grouped AS (
  SELECT user_id, login_date,
         login_date - CAST(ROW_NUMBER() OVER (
             PARTITION BY user_id
             ORDER BY login_date) AS INT) AS grp
  FROM days
)
SELECT user_id,
       MIN(login_date) AS streak_start,
       MAX(login_date) AS streak_end,
       COUNT(*)        AS streak_days
FROM grouped
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;

SQL Server: DATEADD(day, -ROW_NUMBER() OVER (…), login_date). Alternative: flag a new island when login_date - LAG(login_date) > 1, then running-SUM the flags — the same technique as sessions on the next slide.

The main idea

“consecutive”, “streak”, or “continuous range” ⇒ gaps and islands. Deduplicate to one row per unit first, or the trick breaks.

Interview patterns · “a new session starts after 30 minutes of inactivity”

Pattern: sessionize events

Flag starts, then count them

SQL
WITH flagged AS (
  SELECT user_id, event_time,
         CASE
           WHEN event_time - LAG(event_time) OVER (
                  PARTITION BY user_id ORDER BY event_time)
                <= INTERVAL '30 minutes'
           THEN 0
           ELSE 1          -- first event or gap > 30 min
         END AS is_new_session
  FROM events
)
SELECT user_id, event_time,
       SUM(is_new_session) OVER (
         PARTITION BY user_id ORDER BY event_time
         ROWS UNBOUNDED PRECEDING) AS session_no
FROM flagged;

Trace it

event_timegapis_newsession_no

The first event’s LAG is NULL, the comparison is NULL (not true), so ELSE marks it as a new session — exactly what we want.

From here: session length = MAX − MIN per (user, session_no); events per session = COUNT(*).

The main idea

“running SUM of a 0/1 flag” turns change points into group IDs. It solves sessions, islands, and “status changed” problems.

Interview patterns · two classics in one slide

Pattern: Nth highest and “above the group average”

Second-highest order amount

SQL
SELECT MAX(amount) AS second_highest   -- MAX → NULL if none
FROM (
  SELECT amount,
         DENSE_RANK() OVER (ORDER BY amount DESC) AS dr
  FROM orders
) ranked
WHERE dr = 2;

Answer: 40 (not 40, 40, 40). DENSE_RANK makes “second” mean second distinct value; wrapping in MAX returns a single row, or NULL when there is no second value — a common hidden test case.

Orders above their customer’s average

SQL
WITH scored AS (
  SELECT order_id, customer, amount,
         AVG(amount) OVER (PARTITION BY customer)
           AS customer_avg
  FROM orders
)
SELECT order_id, customer, amount, customer_avg
FROM scored
WHERE amount > customer_avg;

Maya’s average is 26.67, so only order 2 (40) qualifies; Leo’s is 50, so order 5 (60). Ana’s single order equals her average and is excluded. Without windows you would need a correlated subquery per row.

The main idea

compare-to-group questions are a window with PARTITION BY and no ORDER BY, followed by an outer filter.

Practice: name the pattern

For each prompt, decide grain, partition, order, and function. Then open the answer.

Find each customer’s first order date and the number of days until their second order.

ROW_NUMBER or LEAD. Partition by customer, order by order_date. LEAD(order_date) OVER (…) - order_date on the row where ROW_NUMBER() = 1. Customers with one order get NULL.

Show each product’s revenue rank within its category; tied products should share a rank and there should be no gaps.

DENSE_RANK partitioned by category, ordered by revenue DESC — after aggregating revenue per product.

Flag days where revenue dropped compared with the previous day.

LAG. Aggregate to one row per day (fill missing days), then revenue < LAG(revenue) OVER (ORDER BY day) in an outer query or CASE.

Find users who placed orders in 3 consecutive months.

Gaps and islands. Distinct (user, month); month index minus ROW_NUMBER gives the island; HAVING COUNT(*) >= 3. Alternatively, LAG(month, 2) equals month − 2 months.

What is wrong with: SELECT *, RANK() OVER (ORDER BY amount) AS r FROM orders WHERE r = 1?

Window functions run after WHERE, and the alias r does not exist yet. Compute in a CTE and filter outside, or use QUALIFY.

The main idea

a strong answer names the pattern, the partition, the order, and one edge case (ties, NULLs, or gaps).

Recursion · WITH RECURSIVE · anchor + recursive member

Recursive CTEs: a loop written as a query

A normal CTE names a query. A recursive CTE refers to itself, so it can keep producing rows until there is nothing new. It is how SQL walks hierarchies of unknown depth and generates sequences.

Count to five

SQL
WITH RECURSIVE numbers AS (
  SELECT 1 AS n               -- anchor member: runs once
  UNION ALL
  SELECT n + 1                -- recursive member
  FROM numbers                --   reads only the previous step
  WHERE n < 5                 --   stop condition
)
SELECT n FROM numbers;        -- 1, 2, 3, 4, 5

What the engine does

01
Anchorworking set = {1}

Runs once. Its rows seed the result.

02
Recursive memberreads {1} → {2}

Sees only the rows produced by the previous step, not the full result.

03
Repeat{2}→{3}→{4}→{5}

Each step’s output becomes the next step’s input.

04
Stop{5} → ∅

When a step returns no rows, the loop ends.

05
ResultUNION ALL of every step

The outer SELECT sees all rows.

The main idea

anchor seeds, recursive member extends, an empty step stops. If nothing in the recursive member can become false, the query never ends.

Generate a calendar to fill missing days

Our orders skip Jan 4, 6, 7, and 8. A report that GROUPs BY date silently drops those days — and rolling averages over ROWS become wrong. Generate every date, then LEFT JOIN the facts.

Build the date spine

SQL
WITH RECURSIVE calendar AS (
  SELECT DATE '2026-01-03' AS cal_date
  UNION ALL
  SELECT cal_date + 1
  FROM calendar
  WHERE cal_date < DATE '2026-01-10'
)
SELECT c.cal_date,
       COALESCE(SUM(o.amount), 0) AS revenue
FROM calendar AS c
LEFT JOIN orders AS o
  ON o.order_date = c.cal_date
GROUP BY c.cal_date
ORDER BY c.cal_date;

Everyone under the CEO, with depth and path

Recursion · hierarchies · three variants interviewers ask for

Down, up, and roll-ups

01Down: all reports of Ben

SQL
WITH RECURSIVE team AS (
  SELECT emp_id, name
  FROM employees WHERE emp_id = 2
  UNION ALL
  SELECT e.emp_id, e.name
  FROM employees AS e
  JOIN team AS t
    ON e.manager_id = t.emp_id
)
SELECT name FROM team
WHERE emp_id <> 2;   -- Dan, Eli, Gus

02Up: Gus’s management chain

SQL
WITH RECURSIVE chain AS (
  SELECT emp_id, name, manager_id
  FROM employees WHERE emp_id = 7
  UNION ALL
  SELECT m.emp_id, m.name, m.manager_id
  FROM employees AS m
  JOIN chain AS c
    ON m.emp_id = c.manager_id   -- flip
)
SELECT name FROM chain;
-- Gus, Dan, Ben, Ava

03Roll-up: bill of materials

SQL
WITH RECURSIVE bom AS (
  SELECT child_part, qty
  FROM components
  WHERE parent_part = 'bike'
  UNION ALL
  SELECT c.child_part, b.qty * c.qty
  FROM components AS c
  JOIN bom AS b
    ON c.parent_part = b.child_part
)
SELECT child_part, SUM(qty) AS total_qty
FROM bom GROUP BY child_part;

Direction is just which side of the join you follow. For roll-ups, carry a multiplied value down the tree, then aggregate in the outer query — most engines forbid aggregates and GROUP BY inside the recursive member.

The main idea

down = join child.manager_id to the previous level; up = join parent.emp_id to the previous level’s manager_id. Aggregate after the recursion, not inside it.

Recursion · safety · and the dialect differences

Make recursion stop: depth limits and cycles

Guard against loops

SQL
WITH RECURSIVE reach AS (
  SELECT to_id,
         ARRAY[from_id, to_id] AS path,
         1 AS hops
  FROM edges WHERE from_id = 'A'
  UNION ALL
  SELECT e.to_id,
         r.path || e.to_id,
         r.hops + 1
  FROM reach AS r
  JOIN edges AS e ON e.from_id = r.to_id
  WHERE e.to_id <> ALL (r.path)   -- not visited yet
    AND r.hops < 10               -- hard depth cap
)
SELECT DISTINCT to_id FROM reach;

Real hierarchies get bad data (A manages B, B manages A). Carry the visited path and refuse to revisit; add a depth cap as a seatbelt. PostgreSQL 14+ also has a built-in CYCLE id SET is_cycle USING path clause.

Dialect differences

EngineKeywordBuilt-in limit
PostgreSQLWITH RECURSIVENone — add your own; CYCLE / SEARCH clauses
MySQL 8WITH RECURSIVEcte_max_recursion_depth = 1000
SQL ServerWITH (no RECURSIVE)OPTION (MAXRECURSION n), default 100
OracleWITH + column listCYCLE clause; legacy CONNECT BY
Snowflake / BigQuery / DuckDBWITH RECURSIVEEngine-specific iteration limits

UNION instead of UNION ALL discards rows already produced, which can stop exact-duplicate cycles — but it costs a dedupe each step and will not catch cycles if a path or depth column makes every row unique.

The main idea

every recursive query needs a reason to stop: data that ends, a visited-check, and a depth cap. Know your engine’s default limit.

Your recursive query runs forever on production data. What happened, and how do you fix it?

A cycle in the data (or a stop condition that never becomes false). Add a visited path check, a depth cap, and on SQL Server keep MAXRECURSION at a sensible value rather than 0.

Clean SQL · formatting and naming

Write SQL for the next reader

Same query, two styles
SQL
select c.customer_name,sum(o.amount) tot,count(*) from customers c,orders o where c.id=o.customer_id and o.order_date>='2026-01-01' group by 1 having count(*)>1 order by 2 desc

It runs. But which join type? What is “tot”? What does “group by 1” mean after someone adds a column?

SQL
SELECT
    c.customer_id,
    c.customer_name,
    SUM(o.amount) AS total_revenue,
    COUNT(*)      AS order_count
FROM customers AS c
INNER JOIN orders AS o
    ON o.customer_id = c.customer_id
WHERE o.order_date >= DATE '2026-01-01'
GROUP BY
    c.customer_id,
    c.customer_name
HAVING COUNT(*) > 1
ORDER BY total_revenue DESC;

One clause per line, explicit JOIN, named aggregates, grouping by the key — and two customers with the same name are no longer merged.

Layout

One column per line; each clause starts a line; indent what belongs to it. Pick upper- or lower-case keywords and stay consistent. Leading or trailing commas — choose one per codebase.

Names

snake_case; descriptive aliases (o for orders is fine, a, b, c is not); name every derived column with AS; avoid reserved words like date or user.

Explicit over implicit

ANSI JOIN … ON, not commas in FROM. Column names, not SELECT * or GROUP BY 1. Qualify columns with their table alias when more than one table is in scope.

The main idea

clean SQL is not decoration: explicit joins, named columns, and grouping by keys prevent real bugs.

Clean SQL · structure · read top to bottom

Use CTEs as named steps

Same logic, two structures
SQL
SELECT customer_id, avg_amount
FROM (
  SELECT customer_id, AVG(amount) AS avg_amount
  FROM (
    SELECT o.customer_id, o.amount
    FROM orders AS o
    WHERE o.status <> 'cancelled'
      AND o.customer_id IN (SELECT customer_id FROM customers WHERE country = 'US')
  ) t1
  GROUP BY customer_id
) t2
WHERE avg_amount > (SELECT AVG(amount) FROM orders WHERE status <> 'cancelled');

Read inside-out. The “not cancelled” rule is written twice and could drift apart.

SQL
WITH valid_orders AS (
    SELECT customer_id, amount
    FROM orders
    WHERE status <> 'cancelled'
),

us_customers AS (
    SELECT customer_id
    FROM customers
    WHERE country = 'US'
),

customer_avg AS (
    SELECT v.customer_id, AVG(v.amount) AS avg_amount
    FROM valid_orders AS v
    INNER JOIN us_customers AS u
        ON u.customer_id = v.customer_id
    GROUP BY v.customer_id
)

SELECT customer_id, avg_amount
FROM customer_avg
WHERE avg_amount > (SELECT AVG(amount) FROM valid_orders);

Read top-down like a recipe. Each step has one job and a name that says what it contains; the business rule lives in one place.

Good CTE habits

Name CTEs after their contents (valid_orders), not their mechanics (t1, cte2). One responsibility each. Filter and select only needed columns early. End with a simple final SELECT.

What CTEs are not

They are not automatically faster. Most engines inline them like subqueries; some (older PostgreSQL before 12, or MATERIALIZED hints) compute them once. Use them for clarity; check the plan for speed.

The main idea

a query built from small named CTEs can be debugged one step at a time: SELECT from any CTE to see its output.

Clean SQL · write queries the optimizer can help

Performance-minded habits

Keep predicates sargable

SQL
-- Hides order_date inside a function:
WHERE EXTRACT(YEAR FROM order_date) = 2026

-- Lets an index or partition pruning work:
WHERE order_date >= DATE '2026-01-01'
  AND order_date <  DATE '2027-01-01'

Sargable (Search ARGument-able) means the engine can use an index, partition, or file statistics to skip data. Keep the column bare; transform the constant instead. A half-open range also handles timestamps correctly.

Small habits, big effects

  • Select only needed columns — essential on columnar storage like Parquet.
  • Filter early, in the CTE that reads the table, not at the end.
  • UNION ALL unless you truly need duplicates removed; UNION adds a sort or hash.
  • EXISTS for “has at least one”, instead of JOIN + DISTINCT.
  • One window, many functions: reuse the same PARTITION BY / ORDER BY (or a named WINDOW) so the engine sorts once.
  • Read the plan with EXPLAIN before guessing.
The main idea

performance in interviews is about intent: show you would filter early, keep predicates sargable, avoid needless sorts, and verify with EXPLAIN.

Clean SQL · applying it to this guide’s topics

Clean habits for windows and recursion

Window functions

SQL
SELECT
    customer,
    order_date,
    amount,
    ROW_NUMBER() OVER by_date AS order_seq,
    SUM(amount)  OVER by_date AS running_total,
    LAG(amount)  OVER by_date AS prev_amount
FROM orders
WINDOW by_date AS (
    PARTITION BY customer
    ORDER BY order_date, order_id      -- unique tie-breaker
    ROWS BETWEEN UNBOUNDED PRECEDING
         AND CURRENT ROW               -- explicit frame
);
  • Name repeated windows once.
  • Always state the frame for running/value functions.
  • End ORDER BY with a unique column.
  • Alias ranks by meaning: amount_rank, not r.

Recursive CTEs

SQL
WITH RECURSIVE org AS (
    -- anchor: top of the hierarchy
    SELECT emp_id, manager_id, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- step: direct reports of the previous level
    SELECT e.emp_id, e.manager_id, o.depth + 1
    FROM employees AS e
    INNER JOIN org AS o
        ON e.manager_id = o.emp_id
    WHERE o.depth < 20                 -- safety cap
)
SELECT emp_id, depth
FROM org;
  • Comment the anchor and the step.
  • Keep the recursive member minimal; enrich in the final SELECT.
  • Put the stop condition where a reader will see it.
  • Carry depth even if the question does not ask for it — it helps debugging.
The main idea

the two hardest-to-read SQL features become easy to review when the frame, tie-breaker, anchor, step, and stop are explicit.

Clean SQL · interviews · a repeatable routine

How to work a SQL interview question

  1. Restate and clarify. “Per customer or overall? How should ties count? Can amounts be NULL? Do cancelled orders count?”
  2. State the grain. Of each input table, and of the output: “one row per customer per month”.
  3. Sketch the CTE steps in words before typing: filter → aggregate to grain → window → filter on window → final columns.
  4. Write it cleanly. Named CTEs, explicit joins, explicit frames, deterministic ORDER BY.
  5. Test on a tiny example. Walk through 4–6 rows including a tie, a NULL, a single-row group, and an empty result.
  6. Mention trade-offs. Alternative approaches (self-join vs LAG, QUALIFY), indexes or partitions, and what changes at large scale.
The main idea

interviewers grade the reasoning as much as the query. Clean structure makes your reasoning visible.

Try it · code review in your head

Practice: spot the problem

SELECT c.name, SUM(o.amount) FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.order_date >= '2026-01-01' GROUP BY c.name

The WHERE on o.order_date discards customers with no orders, turning the LEFT JOIN into an inner join; move it into ON. Also group by c.id (names are not unique) and alias the SUM.

SELECT * FROM products WHERE id NOT IN (SELECT product_id FROM order_items)

If any product_id is NULL, the result is empty. Use NOT EXISTS. Also list the columns you need instead of *.

SELECT o.order_id, SUM(o.amount), COUNT(i.item_id) FROM orders o JOIN order_items i ON i.order_id = o.order_id GROUP BY o.order_id

Fan-out: o.amount is summed once per item. Use MAX(o.amount) at order grain, or aggregate items in a CTE and join to orders.

WHERE DATE(created_at) = '2026-01-05'

Not sargable. Use created_at >= '2026-01-05' AND created_at < '2026-01-06'.

ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) = 1 — the dedupe returns different rows each run.

Ties on updated_at. Add a unique tie-breaker such as the load or event ID.

The main idea

most review comments fall into four buckets: NULLs, grain/fan-out, non-determinism, and sargability.

TermMeaning

Recap · connect each tool to a question

What to remember when you close this deck

Window functions

A window keeps every row and adds a calculation over related rows. Define it as partition → order → frame. Windows run after WHERE and GROUP BY, so filter on them outside.

Ranking for positions and top-N, LAG/LEAD for neighbours, aggregates for running and group totals, distribution for buckets. Always decide ties and frames explicitly.

Recursion and clean SQL

A recursive CTE is anchor + step + stop. Use it for unknown-depth hierarchies, graphs, and generated sequences; guard against cycles with a visited path and depth cap.

Clean SQL means named CTE steps, explicit joins and columns, grouping by keys, NULL-aware logic, sargable filters, and deterministic ordering.

The main idea

name the pattern, state the grain, make ties/frames/stop conditions explicit, and test on a tiny tricky dataset.
