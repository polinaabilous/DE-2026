Why this matters · the need behind the topic

Why this matters on the job

Two things make SQL hard to trust: logic that needs to repeat an unknown number of times, and queries nobody else can read. Recursive CTEs solve the first (hierarchies, calendars, paths); clean structure with named CTE steps solves the second, and it is what code review, dbt projects and interviewers all expect.

Where you will use it

  • Date spines and calendar tables behind every daily metric.
  • Org charts, cost centres, bill-of-materials and category trees.
  • Every dbt model and shared warehouse view: CTE pipelines that others maintain.

What goes wrong without it

  • Hierarchies flattened with a fixed number of self-joins that break at the next level.
  • A recursion over dirty data that never stops (a cycle) and burns warehouse credits.
  • One 300-line query with nested subqueries that nobody dares to change.

Who expects you to know it

  • Analytics engineers and data engineers who write shared transformation code.
  • Interviewers, who judge readability and test recursion with “walk this org chart”.
On the job

An HR analyst asks for headcount under each manager, at any depth. You write a recursive CTE that walks the reporting lines with a depth counter and a visited path, aggregate in a final CTE, and the reviewer can follow every step.

The main idea

recursion handles unknown depth; clean CTE structure makes any query reviewable, testable and safe to change.

02

Recursion · WITH RECURSIVE · anchor + recursive member

Recursive CTEs: a loop written as a query

A normal CTE names a query. A recursive CTE refers to itself, so it can keep producing rows until there is nothing new. It is how SQL walks hierarchies of unknown depth and generates sequences.

Count to five

SQL
WITH RECURSIVE numbers AS (
  SELECT 1 AS n               -- anchor member: runs once
  UNION ALL
  SELECT n + 1                -- recursive member
  FROM numbers                --   reads only the previous step
  WHERE n < 5                 --   stop condition
)
SELECT n FROM numbers;        -- 1, 2, 3, 4, 5

What the engine does

01
Anchorworking set = {1}

Runs once. Its rows seed the result.

02
Recursive memberreads {1} → {2}

Sees only the rows produced by the previous step, not the full result.

03
Repeat{2}→{3}→{4}→{5}

Each step’s output becomes the next step’s input.

04
Stop{5} → ∅

When a step returns no rows, the loop ends.

05
ResultUNION ALL of every step

The outer SELECT sees all rows.

The main idea

anchor seeds, recursive member extends, an empty step stops. If nothing in the recursive member can become false, the query never ends.

Recursion · sequences · the most practical everyday use

Generate a calendar to fill missing days

Our orders skip Jan 4, 6, 7, and 8. A report that GROUPs BY date silently drops those days — and rolling averages over ROWS become wrong. Generate every date, then LEFT JOIN the facts.

Build the date spine

SQL
WITH RECURSIVE calendar AS (
  SELECT DATE '2026-01-03' AS cal_date
  UNION ALL
  SELECT cal_date + 1
  FROM calendar
  WHERE cal_date < DATE '2026-01-10'
)
SELECT c.cal_date,
       COALESCE(SUM(o.amount), 0) AS revenue
FROM calendar AS c
LEFT JOIN orders AS o
  ON o.order_date = c.cal_date
GROUP BY c.cal_date
ORDER BY c.cal_date;

Dialect notes: SQL Server drops RECURSIVE and uses DATEADD(day, 1, cal_date). PostgreSQL also offers generate_series; BigQuery has GENERATE_DATE_ARRAY. In a warehouse, a permanent calendar table is cleaner still.

On the job

A date spine is used in nearly every metrics model: daily revenue must show zero-revenue days, otherwise charts skip days and rolling averages divide by the wrong count. Most warehouses keep a calendar table generated once this way.

The main idea

“include days with zero sales” or “fill the gaps” ⇒ generate the spine, LEFT JOIN facts, COALESCE to zero.

Recursion · hierarchies · step through the iterations

Walk an org chart, one level per step

Everyone under the CEO, with depth and path

SQL
WITH RECURSIVE org AS (
  SELECT emp_id, name, manager_id,
         1 AS depth,
         CAST(name AS VARCHAR(500)) AS path
  FROM employees
  WHERE manager_id IS NULL            -- anchor: the CEO
  UNION ALL
  SELECT e.emp_id, e.name, e.manager_id,
         o.depth + 1,
         CAST(o.path || ' > ' || e.name AS VARCHAR(500))
  FROM employees AS e
  JOIN org AS o
    ON e.manager_id = o.emp_id        -- children of last step
)
SELECT emp_id, name, depth, path
FROM org
ORDER BY path;

The CAST matters: the anchor fixes each column’s type, and a growing string can overflow a short name type (PostgreSQL and SQL Server raise a type-mismatch error).

05

Recursion · hierarchies · three variants interviewers ask for

Down, up, and roll-ups

01Down: all reports of Ben

SQL
WITH RECURSIVE team AS (
  SELECT emp_id, name
  FROM employees WHERE emp_id = 2
  UNION ALL
  SELECT e.emp_id, e.name
  FROM employees AS e
  JOIN team AS t
    ON e.manager_id = t.emp_id
)
SELECT name FROM team
WHERE emp_id <> 2;   -- Dan, Eli, Gus

02Up: Gus’s management chain

SQL
WITH RECURSIVE chain AS (
  SELECT emp_id, name, manager_id
  FROM employees WHERE emp_id = 7
  UNION ALL
  SELECT m.emp_id, m.name, m.manager_id
  FROM employees AS m
  JOIN chain AS c
    ON m.emp_id = c.manager_id   -- flip
)
SELECT name FROM chain;
-- Gus, Dan, Ben, Ava

03Roll-up: bill of materials

SQL
WITH RECURSIVE bom AS (
  SELECT child_part, qty
  FROM components
  WHERE parent_part = 'bike'
  UNION ALL
  SELECT c.child_part, b.qty * c.qty
  FROM components AS c
  JOIN bom AS b
    ON c.parent_part = b.child_part
)
SELECT child_part, SUM(qty) AS total_qty
FROM bom GROUP BY child_part;

Direction is just which side of the join you follow. For roll-ups, carry a multiplied value down the tree, then aggregate in the outer query — most engines forbid aggregates and GROUP BY inside the recursive member.

The main idea

down = join child.manager_id to the previous level; up = join parent.emp_id to the previous level’s manager_id. Aggregate after the recursion, not inside it.

Recursion · safety · and the dialect differences

Make recursion stop: depth limits and cycles

Guard against loops

SQL
WITH RECURSIVE reach AS (
  SELECT to_id,
         ARRAY[from_id, to_id] AS path,
         1 AS hops
  FROM edges WHERE from_id = 'A'
  UNION ALL
  SELECT e.to_id,
         r.path || e.to_id,
         r.hops + 1
  FROM reach AS r
  JOIN edges AS e ON e.from_id = r.to_id
  WHERE e.to_id <> ALL (r.path)   -- not visited yet
    AND r.hops < 10               -- hard depth cap
)
SELECT DISTINCT to_id FROM reach;

Real hierarchies get bad data (A manages B, B manages A). Carry the visited path and refuse to revisit; add a depth cap as a seatbelt. PostgreSQL 14+ also has a built-in CYCLE id SET is_cycle USING path clause.

Dialect differences

EngineKeywordBuilt-in limit
PostgreSQLWITH RECURSIVENone — add your own; CYCLE / SEARCH clauses
MySQL 8WITH RECURSIVEcte_max_recursion_depth = 1000
SQL ServerWITH (no RECURSIVE)OPTION (MAXRECURSION n), default 100
OracleWITH + column listCYCLE clause; legacy CONNECT BY
Snowflake / BigQuery / DuckDBWITH RECURSIVEEngine-specific iteration limits

UNION instead of UNION ALL discards rows already produced, which can stop exact-duplicate cycles — but it costs a dedupe each step and will not catch cycles if a path or depth column makes every row unique.

On the job

Real hierarchy data contains mistakes: an employee recorded as their own manager’s manager creates a cycle. A depth cap and a visited path stop a scheduled job from running until it times out.

The main idea

every recursive query needs a reason to stop: data that ends, a visited-check, and a depth cap. Know your engine’s default limit.

Is a fixed number of self-joins enough?

If the depth is known and small (“employee and their manager”), a self-join is simpler and faster. Recursion is for unknown or variable depth.

What to say

“Anchor is … ; each step joins … to the previous level; it stops when … ; I’ll guard against cycles with a visited path and cap depth at … .”

The main idea

“unknown depth” or “generate rows that are not in any table” are the two signals for a recursive CTE.

Try it · write the anchor and step in your head first

Practice: recursion

For every employee, return the name of their top-level boss.

Anchor: roots (manager_id IS NULL), carrying emp_id AS root_id. Step: children of the previous level inherit root_id. Join root_id back to employees for the name.

Return each employee’s depth and the number of people (direct and indirect) under them.

Walk down from each employee: anchor = every employee as its own top_id; step = children. Then COUNT(*) - 1 GROUP BY top_id. Depth comes from a separate walk from the root.

List every month between a customer’s first and last order, with 0 for months without orders.

Per customer, anchor = first month; step = month + 1 while < last month (join the customer’s bounds). LEFT JOIN monthly revenue, COALESCE to 0.

Your recursive query runs forever on production data. What happened, and how do you fix it?

A cycle in the data (or a stop condition that never becomes false). Add a visited path check, a depth cap, and on SQL Server keep MAXRECURSION at a sensible value rather than 0.

The main idea

if you can say “anchor, step, stop, safety” for a problem, the SQL almost writes itself.

Clean SQL · formatting and naming

Write SQL for the next reader

Same query, two styles
SQL
select c.customer_name,sum(o.amount) tot,count(*) from customers c,orders o where c.id=o.customer_id and o.order_date>='2026-01-01' group by 1 having count(*)>1 order by 2 desc

It runs. But which join type? What is “tot”? What does “group by 1” mean after someone adds a column?

SQL
SELECT
    c.customer_id,
    c.customer_name,
    SUM(o.amount) AS total_revenue,
    COUNT(*)      AS order_count
FROM customers AS c
INNER JOIN orders AS o
    ON o.customer_id = c.customer_id
WHERE o.order_date >= DATE '2026-01-01'
GROUP BY
    c.customer_id,
    c.customer_name
HAVING COUNT(*) > 1
ORDER BY total_revenue DESC;

One clause per line, explicit JOIN, named aggregates, grouping by the key — and two customers with the same name are no longer merged.

Layout

One column per line; each clause starts a line; indent what belongs to it. Pick upper- or lower-case keywords and stay consistent. Leading or trailing commas — choose one per codebase.

Names

snake_case; descriptive aliases (o for orders is fine, a, b, c is not); name every derived column with AS; avoid reserved words like date or user.

Explicit over implicit

ANSI JOIN … ON, not commas in FROM. Column names, not SELECT * or GROUP BY 1. Qualify columns with their table alias when more than one table is in scope.

On the job

Most teams enforce a SQL style automatically (for example SQLFluff in CI with the dbt style rules). Following it makes your pull requests about logic, not formatting.

The main idea

clean SQL is not decoration: explicit joins, named columns, and grouping by keys prevent real bugs.

Clean SQL · structure · read top to bottom

Use CTEs as named steps

Same logic, two structures
SQL
SELECT customer_id, avg_amount
FROM (
  SELECT customer_id, AVG(amount) AS avg_amount
  FROM (
    SELECT o.customer_id, o.amount
    FROM orders AS o
    WHERE o.status <> 'cancelled'
      AND o.customer_id IN (SELECT customer_id FROM customers WHERE country = 'US')
  ) t1
  GROUP BY customer_id
) t2
WHERE avg_amount > (SELECT AVG(amount) FROM orders WHERE status <> 'cancelled');

Read inside-out. The “not cancelled” rule is written twice and could drift apart.

SQL
WITH valid_orders AS (
    SELECT customer_id, amount
    FROM orders
    WHERE status <> 'cancelled'
),

us_customers AS (
    SELECT customer_id
    FROM customers
    WHERE country = 'US'
),

customer_avg AS (
    SELECT v.customer_id, AVG(v.amount) AS avg_amount
    FROM valid_orders AS v
    INNER JOIN us_customers AS u
        ON u.customer_id = v.customer_id
    GROUP BY v.customer_id
)

SELECT customer_id, avg_amount
FROM customer_avg
WHERE avg_amount > (SELECT AVG(amount) FROM valid_orders);

Read top-down like a recipe. Each step has one job and a name that says what it contains; the business rule lives in one place.

Good CTE habits

Name CTEs after their contents (valid_orders), not their mechanics (t1, cte2). One responsibility each. Filter and select only needed columns early. End with a simple final SELECT.

What CTEs are not

They are not automatically faster. Most engines inline them like subqueries; some (older PostgreSQL before 12, or MATERIALIZED hints) compute them once. Use them for clarity; check the plan for speed.

On the job

dbt models are written exactly like this: import CTEs, logical CTEs, a final SELECT. Reviewers can test and reason about each named step.

The main idea

a query built from small named CTEs can be debugged one step at a time: SELECT from any CTE to see its output.

Clean SQL · bugs that return a plausible wrong answer

Correctness traps clean SQL avoids

TrapWhat goes wrongClean fix
= NULLWHERE coupon = NULL is never true; NULL compared with anything is unknown.IS NULL / IS NOT NULL; IS DISTINCT FROM for null-safe comparison.
NOT IN with NULLsWHERE id NOT IN (SELECT ref_id …) returns no rows if any ref_id is NULL.NOT EXISTS (SELECT 1 … WHERE r.ref_id = t.id).
WHERE on a LEFT JOINLEFT JOIN payments p … WHERE p.status = 'ok' removes unmatched rows — it is now an inner join.Move the condition into ON, or state the inner join explicitly.
Join fan-outJoining orders to order_items before SUM(order.amount) counts each order once per item.Aggregate to the right grain in a CTE first, then join. Know each table’s grain.
COUNT confusionCOUNT(*) counts rows; COUNT(col) skips NULLs; COUNT(DISTINCT col) counts unique values.Choose deliberately and name the column accordingly.
Integer division1 / 4 is 0 in PostgreSQL and SQL Server.100.0 * a / NULLIF(b, 0) or CAST to decimal.
Non-determinismLIMIT without ORDER BY; ROW_NUMBER without a unique tie-breaker.Always order by something unique when position matters.
DISTINCT as a bandageDuplicates from a bad join are hidden, not fixed — and cost a sort.Find the fan-out; fix the join or aggregate first.
On the job

These traps produce believable wrong numbers with no error. They are the first things to check when a dashboard total disagrees with finance.

The main idea

before trusting a result, ask “what is the grain of each table, and what happens to NULLs?” Those two questions catch most silent bugs.

Clean SQL · write queries the optimizer can help

Performance-minded habits

Keep predicates sargable

SQL
-- Hides order_date inside a function:
WHERE EXTRACT(YEAR FROM order_date) = 2026

-- Lets an index or partition pruning work:
WHERE order_date >= DATE '2026-01-01'
  AND order_date <  DATE '2027-01-01'

Sargable (Search ARGument-able) means the engine can use an index, partition, or file statistics to skip data. Keep the column bare; transform the constant instead. A half-open range also handles timestamps correctly.

Small habits, big effects

  • Select only needed columns — essential on columnar storage like Parquet.
  • Filter early, in the CTE that reads the table, not at the end.
  • UNION ALL unless you truly need duplicates removed; UNION adds a sort or hash.
  • EXISTS for “has at least one”, instead of JOIN + DISTINCT.
  • One window, many functions: reuse the same PARTITION BY / ORDER BY (or a named WINDOW) so the engine sorts once.
  • Read the plan with EXPLAIN before guessing.
On the job

On cloud warehouses that bill by data scanned (BigQuery, Fabric capacity, Snowflake credits), non-sargable filters and SELECT * cost real money, not just time.

The main idea

performance in interviews is about intent: show you would filter early, keep predicates sargable, avoid needless sorts, and verify with EXPLAIN.

Clean habits for windows and recursion

Window functions

SQL
SELECT
    customer,
    order_date,
    amount,
    ROW_NUMBER() OVER by_date AS order_seq,
    SUM(amount)  OVER by_date AS running_total,
    LAG(amount)  OVER by_date AS prev_amount
FROM orders
WINDOW by_date AS (
    PARTITION BY customer
    ORDER BY order_date, order_id      -- unique tie-breaker
    ROWS BETWEEN UNBOUNDED PRECEDING
         AND CURRENT ROW               -- explicit frame
);
  • Name repeated windows once.
  • Always state the frame for running/value functions.
  • End ORDER BY with a unique column.
  • Alias ranks by meaning: amount_rank, not r.

Recursive CTEs

SQL
WITH RECURSIVE org AS (
    -- anchor: top of the hierarchy
    SELECT emp_id, manager_id, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- step: direct reports of the previous level
    SELECT e.emp_id, e.manager_id, o.depth + 1
    FROM employees AS e
    INNER JOIN org AS o
        ON e.manager_id = o.emp_id
    WHERE o.depth < 20                 -- safety cap
)
SELECT emp_id, depth
FROM org;
  • Comment the anchor and the step.
  • Keep the recursive member minimal; enrich in the final SELECT.
  • Put the stop condition where a reader will see it.
  • Carry depth even if the question does not ask for it — it helps debugging.
The main idea

the two hardest-to-read SQL features become easy to review when the frame, tie-breaker, anchor, step, and stop are explicit.

Try it · code review in your head

Practice: spot the problem

SELECT c.name, SUM(o.amount) FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.order_date >= '2026-01-01' GROUP BY c.name

The WHERE on o.order_date discards customers with no orders, turning the LEFT JOIN into an inner join; move it into ON. Also group by c.id (names are not unique) and alias the SUM.

SELECT * FROM products WHERE id NOT IN (SELECT product_id FROM order_items)

If any product_id is NULL, the result is empty. Use NOT EXISTS. Also list the columns you need instead of *.

SELECT o.order_id, SUM(o.amount), COUNT(i.item_id) FROM orders o JOIN order_items i ON i.order_id = o.order_id GROUP BY o.order_id

Fan-out: o.amount is summed once per item. Use MAX(o.amount) at order grain, or aggregate items in a CTE and join to orders.

WHERE DATE(created_at) = '2026-01-05'

Not sargable. Use created_at >= '2026-01-05' AND created_at < '2026-01-06'.

ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) = 1 — the dedupe returns different rows each run.

Ties on updated_at. Add a unique tie-breaker such as the load or event ID.

The main idea

most review comments fall into four buckets: NULLs, grain/fan-out, non-determinism, and sargability.

Recap · connect each tool to a question

Recap: what to remember when you close this deck

  1. A recursive CTE is anchor + step + stop. Use it for unknown-depth hierarchies, graphs and generated sequences.
  2. Guard every recursion with a depth cap and a visited path; know your engine’s limit (MAXRECURSION, cte_max_recursion_depth).
  3. Generate a calendar once and left-join facts to it, so missing days appear.
  4. Structure queries as named CTE steps that read top to bottom: import, filter, aggregate to grain, join, final select.
  5. Avoid the classic traps: WHERE on the optional side of a LEFT JOIN, NOT IN with NULLs, fan-out before SUM, non-deterministic ORDER BY.
  6. Keep filters sargable and select only the columns you need.
  7. Combine whole result sets with UNION ALL unless you really need duplicates removed (details in the SQL aggregation deck).
The main idea

make the anchor, step and stop explicit, then write the whole query as small named steps a reviewer can check one by one.
