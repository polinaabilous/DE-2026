Why this matters · the need behind the topic

Why this matters on the job

Interviewers and real tickets rarely say “use ROW_NUMBER”. They say “latest record per customer”, “top 3 products per category”, “users active 3 days in a row”, or “split clicks into visits”. Recognising which pattern a question needs is most of the work; the SQL for each pattern is short once you know it.

Where you will use it

  • Silver-layer dedupe of CDC and API feeds: the latest version per key.
  • Leaderboards and “top sellers per category” in reporting models.
  • Product analytics: streaks, retention runs, and sessions from raw events.

What goes wrong without it

  • A dedupe without a tie-breaker returns different rows on every run.
  • Top-N with the wrong ranking function drops or duplicates tied rows.
  • Streak and session logic written as nested self-joins that nobody can review.

Who expects you to know it

  • Data and analytics engineers who own cleaning and metrics models.
  • Timed SQL interviews (DataLemur / LeetCode style): these patterns are most of the medium questions.
On the job

A product manager asks for “how many users had a 7-day login streak last month”. You recognise gaps and islands: one row per user per active day, date minus ROW_NUMBER gives an island key, then count island lengths. Ten minutes, one reviewable query.

The main idea

pattern recognition turns vague business questions into short, standard SQL, and it is exactly what timed SQL interviews measure.

03

Interview patterns · say this out loud before typing

A four-question method for any window problem

  1. What is one output row? (the grain) — one per order? per customer? per day? This tells you whether you need GROUP BY, a window, or both.
  2. Per what? → PARTITION BY. “For each customer” ⇒ PARTITION BY customer. “Overall” ⇒ no partition.
  3. In what order? → ORDER BY inside OVER. “Latest” ⇒ date DESC. “Highest” ⇒ amount DESC. Add a unique tie-breaker.
  4. Which family? position → ranking; neighbour → LAG/LEAD; “so far” / group total → aggregate; bucket → distribution.
  5. Filter after. Put the window in a CTE and filter in the outer query (or QUALIFY where supported). Then test against ties, NULLs, and single-row groups.

Example: “For each customer, return their single biggest order.” Grain: one row per customer. Per: customer. Order: amount DESC, order_id. Family: ranking → ROW_NUMBER (one row, even with ties). Filter: rn = 1.

The main idea

narrating grain → partition → order → family → filter shows the interviewer structured thinking even before the SQL is perfect.

04

Interview patterns · “top 2 orders per customer”

Pattern: top N per group

The query

SQL
WITH ranked AS (
  SELECT customer, order_id, amount,
         DENSE_RANK() OVER (
           PARTITION BY customer
           ORDER BY amount DESC
         ) AS amount_rank
  FROM orders
)
SELECT customer, order_id, amount
FROM ranked
WHERE amount_rank <= 2
ORDER BY customer, amount_rank;

Choosing the ranking function

RequirementUse
Exactly N rows per group, ties broken somehowROW_NUMBER + tie-breaker
Top N values; include everyone tiedDENSE_RANK
Top N positions; ties may push past NRANK

Leo’s result: order 5 (60, rank 1) and order 3 (40, rank 2). Maya: 40 and 25. Ana: only one order, so one row — confirm that is acceptable.

Snowflake / BigQuery / DuckDB shortcut: QUALIFY DENSE_RANK() OVER (…) <= 2.

The main idea

top-N per group = rank inside a partition, filter outside. The interview follow-up is always “what about ties?”

Interview patterns · the most common data-engineering use

Pattern: deduplicate and keep the latest row

A CDC feed delivered the same customer three times. We want the current version of each customer.

Raw rows

customer_idemailupdated_atload_id
7a@old.com2026-01-01 09:001
7a@new.com2026-01-04 12:002
7a@new.com2026-01-04 12:003
8b@x.com2026-01-02 08:001

Keep one row per key

SQL
WITH ranked AS (
  SELECT customer_id, email, updated_at,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY updated_at DESC,
                    load_id    DESC   -- tie-breaker
         ) AS rn
  FROM customer_changes
)
SELECT customer_id, email, updated_at
FROM ranked
WHERE rn = 1;

Why not SELECT DISTINCT? It only removes rows identical in every column. Why not GROUP BY customer_id with MAX(updated_at)? You then need a join back to fetch the other columns — and ties still return duplicates.

On the job

This is the most common Silver-layer transformation: CDC and API feeds deliver several versions of a record, and the pipeline keeps the latest per key. A missing tie-breaker makes nightly runs non-deterministic.

The main idea

“latest per key” and “remove duplicates” are both ROW_NUMBER … = 1. The tie-breaker is what makes the pipeline repeatable.

Interview patterns · “users who logged in 3+ days in a row”

Pattern: consecutive streaks (gaps and islands)

Consecutive dates increase by 1 each day; ROW_NUMBER also increases by 1 each row. Subtract one from the other and every date in the same streak gets the same anchor value.

See the trick

login_daternlogin_date − rnstreak
01-01112-31A
01-02212-31A
01-03312-31A
01-05401-01B
01-06501-01B
01-09601-03C

The query

SQL
WITH days AS (
  SELECT DISTINCT user_id, login_date
  FROM logins                 -- one row per day!
), grouped AS (
  SELECT user_id, login_date,
         login_date - CAST(ROW_NUMBER() OVER (
             PARTITION BY user_id
             ORDER BY login_date) AS INT) AS grp
  FROM days
)
SELECT user_id,
       MIN(login_date) AS streak_start,
       MAX(login_date) AS streak_end,
       COUNT(*)        AS streak_days
FROM grouped
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;

SQL Server: DATEADD(day, -ROW_NUMBER() OVER (…), login_date). Alternative: flag a new island when login_date - LAG(login_date) > 1, then running-SUM the flags — the same technique as sessions on the next slide.

On the job

Streaks (consecutive active days), uptime and outage windows, and “continuous subscription periods” in billing data are gaps-and-islands problems.

The main idea

“consecutive”, “streak”, or “continuous range” ⇒ gaps and islands. Deduplicate to one row per unit first, or the trick breaks.

Interview patterns · “a new session starts after 30 minutes of inactivity”

Pattern: sessionize events

Flag starts, then count them

SQL
WITH flagged AS (
  SELECT user_id, event_time,
         CASE
           WHEN event_time - LAG(event_time) OVER (
                  PARTITION BY user_id ORDER BY event_time)
                <= INTERVAL '30 minutes'
           THEN 0
           ELSE 1          -- first event or gap > 30 min
         END AS is_new_session
  FROM events
)
SELECT user_id, event_time,
       SUM(is_new_session) OVER (
         PARTITION BY user_id ORDER BY event_time
         ROWS UNBOUNDED PRECEDING) AS session_no
FROM flagged;

Trace it

event_timegapis_newsession_no
09:00—11
09:1010m01
09:2515m01
10:3065m12
10:4515m02

The first event’s LAG is NULL, the comparison is NULL (not true), so ELSE marks it as a new session — exactly what we want.

From here: session length = MAX − MIN per (user, session_no); events per session = COUNT(*).

On the job

Product analytics teams turn raw click events into sessions this way before computing session length, bounce rate or conversion per session.

The main idea

“running SUM of a 0/1 flag” turns change points into group IDs. It solves sessions, islands, and “status changed” problems.

Interview patterns · two classics in one slide

Pattern: Nth highest and “above the group average”

Second-highest order amount

SQL
SELECT MAX(amount) AS second_highest   -- MAX → NULL if none
FROM (
  SELECT amount,
         DENSE_RANK() OVER (ORDER BY amount DESC) AS dr
  FROM orders
) ranked
WHERE dr = 2;

Answer: 40 (not 40, 40, 40). DENSE_RANK makes “second” mean second distinct value; wrapping in MAX returns a single row, or NULL when there is no second value — a common hidden test case.

Orders above their customer’s average

SQL
WITH scored AS (
  SELECT order_id, customer, amount,
         AVG(amount) OVER (PARTITION BY customer)
           AS customer_avg
  FROM orders
)
SELECT order_id, customer, amount, customer_avg
FROM scored
WHERE amount > customer_avg;

Maya’s average is 26.67, so only order 2 (40) qualifies; Leo’s is 50, so order 5 (60). Ana’s single order equals her average and is excluded. Without windows you would need a correlated subquery per row.

The main idea

compare-to-group questions are a window with PARTITION BY and no ORDER BY, followed by an outer filter.

Try it · decide before revealing

Practice: name the pattern

For each prompt, decide grain, partition, order, and function. Then open the answer.

Find each customer’s first order date and the number of days until their second order.

ROW_NUMBER or LEAD. Partition by customer, order by order_date. LEAD(order_date) OVER (…) - order_date on the row where ROW_NUMBER() = 1. Customers with one order get NULL.

Show each product’s revenue rank within its category; tied products should share a rank and there should be no gaps.

DENSE_RANK partitioned by category, ordered by revenue DESC — after aggregating revenue per product.

Flag days where revenue dropped compared with the previous day.

LAG. Aggregate to one row per day (fill missing days), then revenue < LAG(revenue) OVER (ORDER BY day) in an outer query or CASE.

Find users who placed orders in 3 consecutive months.

Gaps and islands. Distinct (user, month); month index minus ROW_NUMBER gives the island; HAVING COUNT(*) >= 3. Alternatively, LAG(month, 2) equals month − 2 months.

What is wrong with: SELECT *, RANK() OVER (ORDER BY amount) AS r FROM orders WHERE r = 1?

Window functions run after WHERE, and the alias r does not exist yet. Compute in a CTE and filter outside, or use QUALIFY.

The main idea

a strong answer names the pattern, the partition, the order, and one edge case (ties, NULLs, or gaps).

Clean SQL · interviews · a repeatable routine

How to work a SQL interview question

  1. Restate and clarify. “Per customer or overall? How should ties count? Can amounts be NULL? Do cancelled orders count?”
  2. State the grain. Of each input table, and of the output: “one row per customer per month”.
  3. Sketch the CTE steps in words before typing: filter → aggregate to grain → window → filter on window → final columns.
  4. Write it cleanly. Named CTEs, explicit joins, explicit frames, deterministic ORDER BY.
  5. Test on a tiny example. Walk through 4–6 rows including a tie, a NULL, a single-row group, and an empty result.
  6. Mention trade-offs. Alternative approaches (self-join vs LAG, QUALIFY), indexes or partitions, and what changes at large scale.
The main idea

interviewers grade the reasoning as much as the query. Clean structure makes your reasoning visible.

Quick reference · the words used in this deck

A small glossary to come back to

TermMeaning
PatternA recurring question shape with a known solution, such as top-N per group or gaps and islands.
Signal wordsPhrases in a question that point to a pattern: “latest”, “top 3 per”, “consecutive”, “inactivity gap”.
GrainWhat one output row represents: one per customer, one per day, one per session.
Tie-breakerA unique column added to ORDER BY so a ranking or dedupe gives the same result on every run.
DeduplicateKeep exactly one row per key, usually the latest version (ROW_NUMBER … = 1).
QUALIFYA clause in some engines that filters on window results, like HAVING does for aggregates.
Gaps and islandsFinding continuous runs (islands) and breaks (gaps) in ordered data.
SessionA run of events by one user with no gap longer than an inactivity threshold.

Recap · connect each pattern to a question

Recap: what to remember when you close this deck

  1. Listen for signal words: “top N per” → ranking; “latest / keep one” → ROW_NUMBER; “consecutive” → gaps and islands; “inactivity” → sessions.
  2. Say the four questions out loud: grain, per what, in what order, which family; then filter outside.
  3. Top-N: rank in a CTE, filter outside; choose ROW_NUMBER, RANK or DENSE_RANK by the tie rule.
  4. Dedupe: ROW_NUMBER with a deterministic ORDER BY (add a unique tie-breaker), keep rn = 1.
  5. Gaps and islands: sequence value minus ROW_NUMBER is constant inside a run; group by it.
  6. Sessions: flag a new session with LAG, then a running SUM of the flags numbers the sessions.
  7. In interviews, restate, state the grain, sketch the steps, write cleanly, test on a tiny example.
The main idea

name the pattern first; the SQL for each pattern is short once you recognise it.
