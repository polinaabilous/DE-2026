Why this matters · the need behind the topic

Why this matters on the job

Knowing each technique is not the same as designing a warehouse. Real work, and the modeling round of an interview, starts from vague requirements: you have to find the business processes, decide what to build first, choose every grain, and prove the numbers. This deck practises that end to end.

Where you will use it

  • Kick-off workshops for a new mart or Gold layer.
  • Architecture reviews, where the bus matrix is the one-page plan.
  • Take-home and whiteboard modeling cases in interviews.

What goes wrong without it

  • Teams build facts one dashboard at a time, with dimensions that do not conform.
  • Loads run facts before dimensions and leave orphan keys.
  • Mistakes (mixed grain, summed snapshots, NULL keys) are found by finance, not by tests.

Who expects you to know it

  • Senior data and analytics engineers leading model design.
  • Stakeholders who sign off what gets built first.
  • Interviewers: “design a data model for X” is a standard round.
On the job

A new studio chain asks for revenue, attendance and membership reporting. You list processes (payments, bookings, memberships), draw the bus matrix, agree the grain of each fact, and deliver the first star with tests that reconcile to the source totals.

The main idea

planning with a bus matrix and proving the model with numbers is what turns techniques into a warehouse people trust.

Dimension techniques · the one-page plan of a warehouse

Plan with a bus matrix

A bus matrix lists business processes (future fact tables) as rows and dimensions as columns. A dot means “this process uses this dimension”. Columns with many dots are the dimensions to conform first, because they connect the most processes.

Business process (fact table)DateCustomerProductWarehousePromotionOrder profileWorkshop
Orders · fact_order_line●●●●●●
Fulfilment · fact_order_fulfillment● ×3●●●
Returns · fact_returns●●●●
Inventory · fact_inventory_daily●●●
Promotion coverage · fact_promotion_coverage●●●
Workshops · fact_workshop_attendance●●●

How to read it

Read across a row to see a star schema. Read down a column to see every process a dimension must serve — and everyone who must agree on its definition. “×3” marks a role-playing dimension (the Dimension tables deck).

How to use it

Build the warehouse one row (one business process) at a time, but design the shared columns once. It is also the best artefact to bring to an interview whiteboard or a stakeholder meeting.

On the job

The bus matrix is the one-page plan you bring to a stakeholder or an architecture review: rows are business processes, columns are shared dimensions. It shows what to build first and what must be conformed.

The main idea

the bus matrix turns many separate stars into one coherent warehouse: incremental delivery, shared conformed dimensions.

04

Put it together · dimensions first, then facts, then tests

How a dimensional model is loaded

01
Land raw data in stagingcopy source tables as-is

Keep the original rows so loads can be re-run and audited.

02
Load dimensionsapply SCD rules

Insert new members, overwrite Type 1 attributes, version Type 2 attributes. Make sure the special −1 / −2 rows exist.

03
Load factslook up surrogate keys

For each natural key find the dimension key (by natural key + date for Type 2). If no match: −1 Unknown, or insert an inferred member.

04
Build snapshots and summariesfrom atomic facts

Periodic snapshots at period end; update accumulating snapshots as milestones arrive; aggregates for speed.

05
Testbefore anyone sees the numbers

Grain is unique, no NULL foreign keys, totals reconcile with the source.

Three tests worth automating

SQL
-- 1. Grain: no duplicate rows for the declared grain (expect 0 rows)
SELECT order_number, line_number, COUNT(*) AS copies
FROM fact_order_line
GROUP BY order_number, line_number
HAVING COUNT(*) > 1;

-- 2. No NULL foreign keys (expect 0)
SELECT COUNT(*) FROM fact_order_line
WHERE customer_key IS NULL OR product_key IS NULL OR date_key IS NULL;

-- 3. Reconcile with the source (expect equal totals)
SELECT (SELECT SUM(line_amount) FROM fact_order_line)  AS warehouse_total,
       (SELECT SUM(qty * price)  FROM stg_order_items) AS source_total;

Why dimensions go first

A fact row needs the dimension’s surrogate key at load time. If the dimension has not been refreshed, new customers and new versions are missing and facts would fall back to Unknown.

Tools such as dbt express this order automatically through dependencies, and provide built-in tests for uniqueness, not-null and relationships.

On the job

The load order (dimensions first, then facts with key lookups, then tests) is how dbt DAGs and orchestrated pipelines are arranged; tests on grain and orphan keys run after every load.

The main idea

staging → dimensions → facts → snapshots → tests. The grain-uniqueness test is the single most valuable check on any fact table.

Common modeling mistakes

MistakeSymptomFix
Grain never declared, or mixedTotals double-count; nobody can say what a row isWrite the grain sentence; one grain per fact table; allocate or split
Summing a semi-additive measure over timeStock or balances that grow every day in a monthly reportPeriod-end or average across time; define the measure in the semantic layer
Storing ratios and averagesReport totals that do not match the detailStore numerator and denominator; compute after summing
Natural keys as dimension keysCollisions between sources; Type 2 impossibleSurrogate keys; keep the natural key as an attribute
NULL foreign keysRevenue disappears from joined reportsUnknown / Not applicable members
Joining two fact tables directlyInflated numbers (fan-out)Drill across: aggregate each fact, join on conformed attributes
Every team builds its own dimensionsSame KPI, different answersConformed dimensions planned with a bus matrix
Codes instead of labelsReports full of “3”, “Y”, “ST_02”Decode into readable attributes in the dimension
Snowflaking everythingLong join chains, slow and confusing BI modelsFlatten hierarchies into the dimension
Too many tiny flag dimensionsFact tables with 30 keys (a “centipede”)Junk dimension; question whether each attribute is needed
On the job

These mistakes are the checklist for reviewing someone else’s model or pull request: ask for the grain statement, look for header amounts on line rows, summed snapshots, and NULL foreign keys.

The main idea

nearly every modeling bug shows up as a wrong total. When a number looks off, check grain, additivity, joins, and NULL keys — in that order.

Put it together · what is asked, and what a strong answer includes

Interview cheat-sheet

If you are asked…A strong answer covers
“Design a data model for X.”Clarify questions → list business processes → four steps per process (process, grain, dimensions, facts) → sketch the star → mention SCDs, conformed dims, unknowns
“What is grain? Why does it matter?”What one row represents; declared first; atomic preferred; mixing grains causes double counting (give the shipping-fee example)
“Fact vs dimension?”Measurements of events vs descriptive context; numbers that describe a thing go in the dimension
“Why a star schema?”Simple, few predictable joins, fast, BI-friendly; compare with snowflake and normalized OLTP
“Additive vs semi-additive vs non-additive?”Revenue / account balance / percentage; how each should be aggregated
“Why surrogate keys?”Source collisions, key changes, Type 2 history, unknown members, join performance
“How do you track address changes?”SCD Type 2: new row, new key, valid_from/to, is_current; as-of lookup when loading facts; contrast with Type 1
“Types of fact tables?”Transaction, periodic snapshot, accumulating snapshot (+ factless) with an example and grain for each
“Order date, ship date, delivery date — how?”Role-playing dim_date with three foreign keys and aliases or views
“Where does order number go?”Degenerate dimension on the fact table
“Customer in many segments?”Bridge table; weighting factor; warn about double counting
“Missing dimension values?”Unknown / Not applicable rows, never NULL keys; inferred members for late arrivals
On the job

The same questions come up in design reviews at work, not only in interviews. Having a one-sentence answer and a concrete example for each makes those discussions short.

The main idea

interviewers reward structure: state the grain, name the technique, give a concrete example, and mention the trap it avoids.

07

Try it · decide, then reveal

Quick checks before the project

A table has one row per customer per month with the column loyalty_points_balance. What kind of fact table is it, and how should balances be totalled for a year?

Periodic snapshot. The balance is semi-additive: sum across customers for one month, but for a year take the December (closing) value or the average — never the sum of 12 months.

A support ticket moves from opened → assigned → resolved → closed, and managers want time spent in each step. Which fact table type?

Accumulating snapshot: one row per ticket, a role-playing date key per milestone, lag measures between them, updated as the ticket progresses.

A product’s category was wrong for a month because of a data-entry typo. Type 1 or Type 2?

Type 1. It is a correction; history should show the right category everywhere. Type 2 would preserve a mistake.

Every sale has an invoice number and nothing else about the invoice is descriptive. Where does invoice_number go?

On the fact table as a degenerate dimension.

A hospital visit can have several diagnoses. Revenue by diagnosis adds up to more than total revenue. Is something broken?

Not necessarily: this is a bridge table (many-to-many) and overlapping totals are expected. Either label it “revenue from visits with this diagnosis” and do not total it, or use a weighting factor so allocated revenue reconciles.

Which students were enrolled in a course but never attended a lecture? What two fact tables do you need?

A coverage factless fact (enrolment: student × course × term) and an event factless fact (attendance). Enrolled minus attended = the answer.

The main idea

if you can answer all six with a reason, you are ready to model a business from scratch.

Practice project · the brief

Project: model FitHub’s studios

FitHub runs fitness studios in Austin and Denver. Members buy a monthly plan (Basic, Plus, Premium) after a free trial, and book group classes — yoga, spin, HIIT — through the app, the website, or the front desk. Some classes are co-taught by two instructors. Walk-in visitors can pay for a single class without being members. FitHub’s financial year starts on 1 July.

Leadership wants a dimensional model that answers these questions. Your job is to design it, build it on the sample data, and answer them:

  1. Revenue in March 2026 by member home city (as it was at the time of payment) and by payment type — walk-ins included.
  2. Attendance rate by class type: attended bookings ÷ bookings that were not cancelled in advance.
  3. Attended visits credited to instructors, with co-taught classes shared fairly so the total matches attended bookings.
  4. Active paying members by plan on 31 January 2026, as they were on that date (not as they are today).
  5. Scheduled classes that received no bookings at all.
  6. Days from trial start to paid conversion for each member, and the average for those who converted.

What you will practise

Business processes and a bus matrix, grain statements, all three fact table types plus a factless fact, additivity, surrogate keys, SCD Type 1 and 2, role-playing dates, degenerate IDs, a junk dimension, unknown members, a bridge table, conformed dimensions, and a date dimension with a fiscal calendar.

Tools

Pen and paper for the design. To build it, any SQL engine works; DuckDB is ideal because it is free, needs no server, and reads CSV files directly. Expect 3–5 hours for the full project.

On the job

This is the shape of a real first assignment on an analytics team: a short brief, a handful of source extracts, and questions the business wants answered by the end of the week.

The main idea

this is a realistic, small-scale version of a real modeling assignment. The sample data is tiny on purpose, so you can check every number by hand.

Practice project · work through these in order

Project: your tasks, step by step

  1. Find the business processes. List the events FitHub records (hint: there are at least five). Draw a bus matrix of processes × dimensions.
  2. Declare the grain of each fact table in one sentence, and name its type: transaction, periodic snapshot, accumulating snapshot, or factless.
  3. Design the dimensions. List attributes, flatten hierarchies, replace codes with labels, and assign surrogate keys. Decide which dimensions are conformed.
  4. Choose SCD types for every member attribute. Rebuild dim_member as Type 2 from members.csv + member_changes.csv (trial counts as its own “plan”).
  5. Classify every measure as additive, semi-additive or non-additive, and decide how each should be aggregated.
  6. Handle the special cases: the several dates on a booking, booking and payment IDs, the small booking flags, the walk-in payment, the co-taught class, and the class nobody booked.
  7. Build it in SQL: dim_date with a July fiscal year, then the dimensions (with −1 / −2 rows), then the facts with surrogate-key lookups.
  8. Answer the six questions from the brief with SQL against your model — not against the staging tables.
  9. Write three tests: grain uniqueness for each fact, no NULL foreign keys, and payments reconciling to the source total.

Deliverables

A one-page diagram (bus matrix + stars), a short document with grain sentences and design decisions, the SQL scripts, and your six answers.

Stretch goals

Add dim_time_of_day and report attendance by morning / lunchtime / evening. Build a month-end membership snapshot for January–March. Expose the model in Power BI and check the relationships are all one-to-many from dimensions to facts.

The main idea

do steps 1–6 on paper before writing any SQL. Most of the learning — and most interview credit — is in the design decisions.

Project: hints if you get stuck

Hint 1 · Which business processes are there?

Think in verbs: members book classes; FitHub schedules classes; people pay; members hold a plan each month; trials convert (or not). Each verb is a candidate fact table.

Hint 2 · Is a scheduled class a dimension or a fact?

Both views are defensible. A class session has descriptive attributes (studio, type, start time) — those become dimensions on the booking fact, with class_id as a degenerate dimension. The schedule itself is a coverage-style factless fact (one row per scheduled class, optionally with capacity), which is exactly what you need for “classes with no bookings”.

Hint 3 · How do I rebuild member history?

Each member starts with a TRIAL version from trial_start until the day before converted_on. Then a paid version begins. For members in member_changes.csv, the first paid version uses the old values and ends the day before changed_on; a new version with the new values starts on changed_on. Everyone’s last version is current, valid to 9999-12-31.

Hint 4 · Where do channel, status, waitlisted and guest pass go?

They are low-cardinality booking flags: a junk dimension (dim_booking_profile). Also add 0/1 measures such as attended_count and no_show_count on the fact so rates are easy sums.

Hint 5 · Which dates does a booking have?

Booked date, class date, and cancellation date — three roles of one dim_date. Bookings that were never cancelled use the −2 “Not applicable” date row, not NULL.

Hint 6 · How do I share credit for C901?

Create instructor groups: each class points at a group, and bridge_instructor_group lists the instructors in it with weights summing to 1 (0.5 and 0.5 for Dev and Kim).

Hint 7 · What member does the walk-in payment get?

P703 has no member by design, so it is not “unknown” — use the −2 Not applicable member (label it “Walk-in / non-member”). Reserve −1 Unknown for member IDs that are missing by mistake or do not match.

The main idea

every hint maps to a lesson: processes (16), factless (31), Type 2 (23–24), junk (36), role-playing (34), bridge (38), unknown members (37).

Recap · the ideas that carry everything else

Recap: what to remember when you close this deck

  1. Start a warehouse with a bus matrix: one row per business process, one column per shared dimension.
  2. Apply the four steps to each process: process, grain, dimensions, facts.
  3. Load dimensions first, then facts with key lookups (and Unknown rows), then test grain, keys and totals.
  4. Most modeling bugs show up as a wrong total: check grain, additivity, joins and NULL keys, in that order.
  5. In interviews, state the grain, name the technique, give a concrete example, and mention the trap it avoids.
The main idea

a good model is planned on one page, built in a fixed order, and proven with numbers that reconcile.
