Window functions: OVER, partitions, ordering, frames, and every function family.

A window function adds a calculation over related rows without collapsing them. It answers “what share of the customer’s spend is this order?”, “what was the previous order?”, and “what is the running total?” in one pass.

Every example uses the same six orders, so you can check each result by hand.

Why this matters · the need behind the topic

Why this matters on the job

Most analytics questions compare a row with related rows: its share of the customer total, the previous order, the running total so far. Window functions answer these in one readable pass, without self-joins, and they are the single most tested SQL topic in data interviews.

Where you will use it

  • dbt models and warehouse views: running totals, rankings, percent-of-total columns.
  • Period-over-period metrics in business reviews (LAG over monthly aggregates).
  • Silver-layer cleaning: ROW_NUMBER to pick one version of each record.

What goes wrong without it

  • Self-joins and correlated subqueries that are slow and hard to review.
  • Running totals that jump on tied dates because of the default RANGE frame.
  • Rankings that change between runs because ties were never decided.

Who expects you to know it

  • Data engineers, analytics engineers and BI developers.
  • Live SQL interviews: ROW_NUMBER vs RANK vs DENSE_RANK, LAG/LEAD and frames come up in most loops.
On the job

A finance analyst asks for each customer’s orders with a running balance and the change from the previous order. With windows it is one SELECT over the orders table: SUM(...) OVER (PARTITION BY customer ORDER BY order_date ROWS UNBOUNDED PRECEDING) and amount - LAG(amount) OVER (...).

The main idea

window functions give each row context from related rows; they are a daily transformation tool and an interview staple.

Window basics · the one idea everything else builds on

GROUP BY collapses rows. A window keeps them.

Both queries add up amounts per customer. The difference is what happens to the rows.

Compare the two results
SQL
SELECT customer, SUM(amount) AS customer_total
FROM orders
GROUP BY customer;
customercustomer_total
Ana40
Leo100
Maya80

Six rows went in, three came out. The individual orders are gone.

SQL
SELECT order_id, customer, amount,
       SUM(amount) OVER (PARTITION BY customer) AS customer_total
FROM orders;
order_idcustomeramountcustomer_total
1Maya2580
2Maya4080
3Leo40100
4Maya1580
5Leo60100
6Ana4040

Six rows went in, six came out. Each order also carries its customer’s total.

What is a window?

A window is the set of rows a function is allowed to look at for the current row. OVER (…) defines it.

Why it matters

You can now compare a row with its group in one pass: “what share of Maya’s spend is order 2?” needs both the order amount and Maya’s total on the same row.

On the job

Analysts ask for “each order with its share of the customer’s spend” all the time. In a dbt model or a warehouse view this is one window aggregate, not a GROUP BY joined back to the detail rows.

The main idea

if the question needs detail rows and a group-level number side by side, you want a window function, not GROUP BY.

03

Window basics · three optional parts, always in this order

The anatomy of OVER ( )

SQL
function_name(args) OVER (
    PARTITION BY customer          -- 1. split rows into independent groups
    ORDER BY order_date            -- 2. sort rows inside each group
    ROWS BETWEEN UNBOUNDED PRECEDING
         AND CURRENT ROW           -- 3. frame: which sorted rows count right now
)

01PARTITION BY

“Per what?” Restarts the calculation for each group. Leave it out and the whole result set is one partition.

02ORDER BY

“In what sequence?” Required for ranking and LAG/LEAD. For aggregates it turns a group total into a running total.

03Frame

“Which rows up to or around me?” Only used by aggregate and value functions. If you omit it, a default applies — next slides.

The main idea

read every window aloud as “for each partition, in order, looking at frame”. If you cannot finish that sentence, the query is not ready.

04

Window basics · logical query processing order

When do window functions run?

SQL is written SELECT-first but evaluated in a different order. Windows are computed late — after grouping, before the final sort.

01
FROM / JOINbuild the row set

Tables are combined.

02
WHEREfilter rows

Window results do not exist yet, so you cannot filter on them here.

03
GROUP BY → HAVINGaggregate and filter groups

Windows see the grouped rows, so SUM(SUM(amount)) OVER () is legal.

04
Window functionscompute OVER (…)

Evaluated on the rows that survived.

05
SELECT → DISTINCTpick and dedupe columns

Aliases are created here.

06
ORDER BY → LIMITsort and cut

You may ORDER BY a window alias.

So how do I filter on a rank?

Wrap it: compute the window in a CTE, filter in the outer query. Some engines (Snowflake, BigQuery, Databricks, DuckDB, Teradata) add QUALIFY as a shortcut.

Example

SQL
WITH ranked AS (
  SELECT order_id, customer,
         ROW_NUMBER() OVER (PARTITION BY customer
                            ORDER BY order_date DESC) AS rn
  FROM orders
)
SELECT order_id, customer
FROM ranked
WHERE rn = 1;   -- each customer's latest order
On the job

Knowing the logical order explains real errors you will meet in Fabric, Snowflake or Databricks: “window functions are not allowed in WHERE” means the filter must move to an outer query or QUALIFY.

The main idea

“window function in WHERE” is a classic interview error. Say it out loud: “windows run after WHERE, so I’ll filter in an outer query.”

Window basics · the default frame is the #1 window gotcha

Frames: which rows count “so far”?

Orders 2 and 3 share the date 2026-01-05. Watch what that does to a running total under each frame.

Pick a frame

SELECT order_id, order_date, amount,
       SUM(amount) OVER (ORDER BY order_date) AS s

With ORDER BY and no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Rows with the same date are peers and are added together.

A sliding frame: this row plus the one before it. This is how moving averages and rolling sums are built.

SQL
SELECT order_id, order_date, amount,
       SUM(amount) OVER () AS s

With no ORDER BY the frame is the whole partition, so every row sees the grand total.

ROWS = count physical rows. RANGE = include every row whose ORDER BY value falls in the range (all peers). Some engines also support RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW and GROUPS.

On the job

Running balances in finance marts and cumulative sign-ups on dashboards are where the default RANGE frame bites: tied dates silently jump together. Reviewers ask for an explicit ROWS frame.

The main idea

whenever you write ORDER BY inside OVER for a SUM/AVG/LAST_VALUE, write the frame explicitly. It documents intent and removes the tie surprise.

Window functions · a map before the details

Five families of window functions

FamilyFunctionsQuestion it answersORDER BY?
RankingROW_NUMBERRANKDENSE_RANKWhere does this row place in its group?Required
DistributionNTILEPERCENT_RANKCUME_DISTWhich bucket or percentile is this row in?Required
OffsetLAGLEADWhat was on the previous / next row?Required
ValueFIRST_VALUELAST_VALUENTH_VALUEWhat is the first / last / Nth value in the frame?Required in practice; watch the frame
AggregateSUMAVGCOUNTMINMAXWhat is the total so far, or for the whole group?Optional: with it = running; without = whole group

Ranking, distribution and offset functions ignore any frame — they always look at the whole partition. Only value and aggregate functions use the frame.

The main idea

identify the family first (“I need a position / a neighbour / a running number”), then pick the exact function.

Window functions · ranking · ROW_NUMBER()

ROW_NUMBER: a unique sequence per group

Number each customer’s orders

SQL
SELECT customer, order_date, order_id,
       ROW_NUMBER() OVER (
         PARTITION BY customer
         ORDER BY order_date, order_id
       ) AS order_seq
FROM orders;
customerorder_dateorder_seq
Ana2026-01-101
Leo2026-01-051
Leo2026-01-102
Maya2026-01-031
Maya2026-01-052
Maya2026-01-093

How it behaves

Always 1, 2, 3… with no gaps and no ties, even if two rows are identical on the ORDER BY columns.

That means ties are broken arbitrarily unless you add a tie-breaker. Two runs of the same query can number tied rows differently — a real source of flaky pipelines.

Use it for: “exactly one row per group” (dedupe, latest record), first purchase vs repeat purchase, pagination, and the gaps-and-islands trick.

The main idea

ROW_NUMBER guarantees exactly one row per position. Always end its ORDER BY with a unique column so the result is deterministic.

08

Window functions · ranking · the tie question

ROW_NUMBER vs RANK vs DENSE_RANK

Rank all orders by amount, highest first. Three orders tie at 40.

SQL
SELECT order_id, amount,
       ROW_NUMBER() OVER (ORDER BY amount DESC) AS row_number,
       RANK()       OVER (ORDER BY amount DESC) AS rank,
       DENSE_RANK() OVER (ORDER BY amount DESC) AS dense_rank
FROM orders;

order_idamountROW_NUMBERRANKDENSE_RANK
560111
240222
340322
640422
125553
415664

RANK — “Olympic” ranking

Ties share a rank, then the next rank skips (1, 2, 2, 2, 5). Use when position should reflect how many rows are ahead.

DENSE_RANK — no gaps

Ties share a rank, next rank is consecutive (1, 2, 2, 2, 3). Use for “Nth highest distinct value” and “top 3 salary levels”.

ROW_NUMBER — no ties

Forces 2, 3, 4 on the tied rows. Order among them is arbitrary here — add order_id to make it stable.

On the job

Leaderboards, “top sellers” reports and ranking features for ML all depend on the tie rule. Write the rule (shared rank, gaps or not) into the model’s documentation, not just the SQL.

The main idea

in an interview, ask “how should ties be handled?” before writing a ranking query. The answer picks the function.

Window functions · distribution · buckets and percentiles

NTILE, PERCENT_RANK, CUME_DIST

SQL
SELECT order_id, amount,
       NTILE(4)       OVER (ORDER BY amount DESC) AS quartile,
       PERCENT_RANK() OVER (ORDER BY amount DESC) AS pct_rank,
       CUME_DIST()    OVER (ORDER BY amount DESC) AS cume_dist
FROM orders;

order_idamountNTILE(4)PERCENT_RANKCUME_DIST
56010.000.17
24010.200.67
34020.200.67
64020.200.67
12530.800.83
41541.001.00

NTILE(n)

Deals rows into n buckets as evenly as possible; earlier buckets get the extra rows (6 rows / 4 = 2, 2, 1, 1). Ties can be split across buckets — orders 2 and 3 both have 40 but land in different quartiles.

PERCENT_RANK

(rank − 1) / (rows − 1). Ranges 0 to 1. “What fraction of rows are ranked above me?” Ties share a value.

CUME_DIST

rows at or before me (including peers) / rows. Ranges just above 0 to 1. “Top 10%” ⇒ CUME_DIST() <= 0.10 when ordering descending.

The main idea

NTILE for “split into equal-size groups”; PERCENT_RANK / CUME_DIST for “top X percent” where ties must stay together.

Window functions · offset · LAG(col, n, default) / LEAD(col, n, default)

LAG and LEAD: look at the neighbour row

Maya’s order-to-order change

SQL
SELECT order_date, amount,
       LAG(amount)  OVER w AS prev_amount,
       LEAD(amount) OVER w AS next_amount,
       amount - LAG(amount) OVER w AS change,
       order_date - LAG(order_date) OVER w
                                AS days_since_prev
FROM orders
WHERE customer = 'Maya'
WINDOW w AS (PARTITION BY customer
             ORDER BY order_date);
order_dateamountprevnextchangedays
01-0325NULL40NULLNULL
01-05402515+152
01-091540NULL−254

How it behaves

LAG(x) returns x from the previous row in the window order; LEAD(x) from the next. The optional second argument is the offset (LAG(x, 7)), the third is a default instead of NULL (LAG(x, 1, 0)).

The first row has no predecessor, so LAG returns NULL — and any arithmetic with it is NULL. Decide whether that should be NULL, 0, or filtered out.

The WINDOW w AS (…) clause names a window once and reuses it (PostgreSQL, MySQL 8, SQLite, BigQuery, DuckDB, SQL Server 2022).

Use it for: month-over-month change, time between events, detecting status changes, sessionization.

On the job

Change-since-last-period metrics, “days since previous order”, and detecting status changes in CDC feeds are LAG/LEAD in everyday pipelines.

The main idea

whenever a question compares a row with “the previous one” or “the next one”, reach for LAG/LEAD instead of a self-join.

Window functions · value · and the LAST_VALUE trap

FIRST_VALUE, LAST_VALUE, NTH_VALUE

Run LAST_VALUE with two frames
SQL
SELECT order_date, amount,
       FIRST_VALUE(amount) OVER (PARTITION BY customer ORDER BY order_date) AS first_amt,
       LAST_VALUE(amount)  OVER (PARTITION BY customer ORDER BY order_date) AS last_amt
FROM orders WHERE customer = 'Maya';
order_dateamountfirst_amtlast_amt
01-03252525
01-05402540
01-09152515

LAST_VALUE just echoes the current row: the default frame stops at CURRENT ROW, so the “last” row in the frame is me.

SQL
SELECT order_date, amount,
       FIRST_VALUE(amount)  OVER w AS first_amt,
       LAST_VALUE(amount)   OVER w AS last_amt,
       NTH_VALUE(amount, 2) OVER w AS second_amt
FROM orders WHERE customer = 'Maya'
WINDOW w AS (PARTITION BY customer ORDER BY order_date
             ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING);
order_dateamountfirst_amtlast_amtsecond_amt
01-0325251540
01-0540251540
01-0915251540

With the frame widened to the whole partition, every row sees Maya’s first, last, and second order amounts.

Tip: LAST_VALUE(x) OVER (ORDER BY d) can also be written as FIRST_VALUE(x) OVER (ORDER BY d DESC), which needs no frame. NTH_VALUE is not available in SQL Server.

On the job

Opening and closing balances, first touch / last touch attribution and “first status of the day” use value functions; the LAST_VALUE frame trap is a frequent bug in production reports.

The main idea

value functions respect the frame. For “first/last in the group”, use a full frame or flip the sort and use FIRST_VALUE.

Window functions · aggregate · same functions, new superpower

SUM, AVG, COUNT, MIN, MAX as windows

SQL
SELECT customer, order_date, amount,
       SUM(amount) OVER (PARTITION BY customer ORDER BY order_date
                         ROWS UNBOUNDED PRECEDING)          AS running_total,
       ROUND(100.0 * amount
             / SUM(amount) OVER (PARTITION BY customer), 1) AS pct_of_customer,
       amount - AVG(amount) OVER ()                         AS vs_avg
FROM orders
WHERE customer = 'Maya';   -- note: AVG OVER () here is Maya's average, because WHERE ran first

order_dateamountrunning_totalpct_of_customervs_avg
01-03252531.3−1.67
01-05406550.0+13.33
01-09158018.8−11.67

With ORDER BY → running

Cumulative revenue, running count of orders, “max so far” (MAX(x) OVER (ORDER BY d)) for record highs.

Without ORDER BY → whole group

Share of total, difference from group average, “flag rows above their group’s mean”. Multiply by 100.0 to avoid integer division.

Windows over aggregates

Because windows run after GROUP BY: SUM(amount) * 100.0 / SUM(SUM(amount)) OVER () gives each customer’s share of all revenue in one grouped query.

On the job

Moving averages for monitoring dashboards and “percent of total” columns in semantic models are window aggregates; they keep the detail rows that BI tools need for drill-down.

The main idea

every aggregate you know becomes a window function by adding OVER. ORDER BY in the window decides “so far” vs “whole group”.

Interview patterns · “cumulative revenue” and “7-day rolling average”

Pattern: running totals and moving averages

Aggregate to the grain first

SQL
WITH daily AS (
  SELECT order_date, SUM(amount) AS revenue
  FROM orders
  GROUP BY order_date
)
SELECT order_date, revenue,
       SUM(revenue) OVER (ORDER BY order_date
             ROWS UNBOUNDED PRECEDING)          AS cumulative_revenue,
       AVG(revenue) OVER (ORDER BY order_date
             ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
                                                AS rolling_7_row_avg
FROM daily;

Two traps interviewers probe

Missing days. ROWS 6 PRECEDING means 6 rows, not 6 days. Our data has no orders on Jan 4, 6, 7, 8, so a “7-row” window spans far more than a week. Fix: join to a calendar (recursive CTE, later) or use RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW where supported.

Partial windows. The first six days average fewer than 7 values. If that matters, also compute COUNT(*) OVER (same frame) and show NULL when it is below 7.

On the job

Cumulative revenue, month-to-date targets and 7-day rolling averages in KPI dashboards are window aggregates. Fill missing days first (a date spine) or the ROWS frame counts the wrong days.

The main idea

aggregate to one row per period, make sure every period exists, then apply an explicit ROWS frame.

Interview patterns · month-over-month, year-over-year

Pattern: period-over-period change

Month-over-month growth

SQL
WITH monthly AS (
  SELECT DATE_TRUNC('month', order_date) AS month,
         SUM(amount)                     AS revenue
  FROM orders
  GROUP BY DATE_TRUNC('month', order_date)
)
SELECT month, revenue,
       LAG(revenue) OVER w AS prev_revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER w)
             / NULLIF(LAG(revenue) OVER w, 0), 1) AS pct_change
FROM monthly
WINDOW w AS (ORDER BY month);

Details that earn points

Year-over-year on monthly rows: LAG(revenue, 12) OVER (ORDER BY month) — only correct if all 12 months exist. Safer: self-join on month - INTERVAL '1 year', or fill months first.

Divide safely: NULLIF(prev, 0) avoids divide-by-zero; 100.0 avoids integer division.

Per segment: add PARTITION BY region so each region compares with its own previous month.

On the job

Month-over-month and year-over-year columns in business reviews are LAG over a monthly aggregate. Check that every period exists first, otherwise LAG compares with the wrong month.

The main idea

period-over-period = aggregate per period, then LAG. Mention gaps and divide-by-zero before the interviewer does.

Try it · decide before revealing

Practice: name the pattern

For each prompt, decide grain, partition, order, and function. Then open the answer.

Find each customer’s first order date and the number of days until their second order.

ROW_NUMBER or LEAD. Partition by customer, order by order_date. LEAD(order_date) OVER (…) - order_date on the row where ROW_NUMBER() = 1. Customers with one order get NULL.

Show each product’s revenue rank within its category; tied products should share a rank and there should be no gaps.

DENSE_RANK partitioned by category, ordered by revenue DESC — after aggregating revenue per product.

Flag days where revenue dropped compared with the previous day.

LAG. Aggregate to one row per day (fill missing days), then revenue < LAG(revenue) OVER (ORDER BY day) in an outer query or CASE.

Find users who placed orders in 3 consecutive months.

Gaps and islands. Distinct (user, month); month index minus ROW_NUMBER gives the island; HAVING COUNT(*) >= 3. Alternatively, LAG(month, 2) equals month − 2 months.

What is wrong with: SELECT *, RANK() OVER (ORDER BY amount) AS r FROM orders WHERE r = 1?

Window functions run after WHERE, and the alias r does not exist yet. Compute in a CTE and filter outside, or use QUALIFY.

The main idea

a strong answer names the pattern, the partition, the order, and one edge case (ties, NULLs, or gaps).

Quick reference · the words used in this deck

A small glossary to come back to

TermMeaning
WindowThe set of rows a window function can see for the current row, defined by OVER (…).
PartitionAn independent group of rows inside a window (PARTITION BY). Calculations restart per partition.
FrameThe subset of the sorted partition used right now: ROWS, RANGE, or GROUPS BETWEEN … AND ….
Default frameWith ORDER BY and no frame clause: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which includes tied peers.
PeersRows with equal ORDER BY values. RANGE frames and RANK treat them together.
Ranking / offset / value / aggregate / distribution functionsThe five window families: positions; neighbour rows; first/last/nth values; sums and averages; buckets and percentiles.
Running totalA cumulative sum over the rows so far, in a stated order.
QUALIFYA clause in some engines that filters on window results, like HAVING does for aggregates.
GrainWhat one row represents: one order, one customer per day, one event.
17

Recap · connect each tool to a question

Recap: what to remember when you close this deck

  1. A window keeps every row and adds a calculation over related rows; GROUP BY collapses them.
  2. Read every window as partition → order → frame. Leave out PARTITION BY and the whole result is one partition.
  3. Windows run after WHERE, GROUP BY and HAVING; filter on them in an outer query or with QUALIFY.
  4. With ORDER BY and no frame, the default RANGE frame includes tied rows. Write ROWS BETWEEN … when you mean rows.
  5. ROW_NUMBER never ties, RANK leaves gaps, DENSE_RANK does not. Decide ties before choosing.
  6. LAG/LEAD replace self-joins for “previous / next”; the first row gets NULL unless you give a default.
  7. LAST_VALUE needs a full frame (or flip the sort and use FIRST_VALUE).
The main idea

name the partition, the order and the frame out loud; then the function choice is usually obvious.
